# Localzet Weather · v0.1

Погодный веб-сервис для пяти городов России: Ростов-на-Дону, Екатеринбург, Североуральск, Карпинск, Краснотурьинск.

## Публикация

Статический сайт: [localzet.github.io/weather/](https://localzet.github.io/weather/) (после включения **Settings → Pages → Source → GitHub Actions**). Автоматическая публикация настроена через [weather-pages.yml](../../.github/workflows/weather-pages.yml). Никакой сборки, ключей или сервера для интерфейса не нужно.

## Что работает

- Current forecast, почасовая температура и вероятность осадков, 7-дневный прогноз;
- переключение между городами и ссылка с `?city=...`;
- локальный кэш с TTL 15 минут и режимом деградации, если API недоступен;
- мобильный интерфейс;
- раздел о принципах объективной проверки точности.

**Важно:** текущие прогнозы приходят из Open-Meteo (автоматически выбранные численные модели) и **не являются собственной корректирующей моделью**. Никаких необоснованных обещаний «самый точный прогноз» на сайте нет.

## Архивирование моделей

Файл [scripts/collect.py](./scripts/collect.py) по расписанию через [GitHub Actions](../../.github/workflows/weather-collect.yml) собирает прогнозы по трём независимым API Open-Meteo:

- `/v1/ecmwf`;
- `/v1/gfs`;
- `/v1/dwd-icon`.

Для каждого из пяти городов сохраняются почасовые температурные и осадочные прогнозы на пять суток. Операционные снимки сохраняются с шагом 6 часов в `archive/YYYY/MM/DD/HH.json.gz`. При сбоях отдельных источников записываются ошибки; если не ответил ни один источник, архив не создаётся.

Ключевое ограничение: поле `captured_at` обозначает время доступности прогноза при запросе, **а не официальный `issued_at` выпуска исходной численной модели**. Независимую верификацию выполняет отдельный [WeatherBench](./scripts/bench.py); его результаты публикуются в [data/accuracy.json](./data/accuracy.json).

GitHub scheduled workflows могут задерживаться или не выполняться при ограничениях Actions; поэтому такой сбор подходит для исследовательского прототипа, но не гарантирует беспрерывной записи данных. Для будущего production следует перенести архивирование в сервис с наблюдаемостью, ретраями и постоянным объектным хранилищем.

## Независимая верификация: WeatherBench

[Скрипт](./scripts/bench.py) сопоставляет сохранённые прогнозы с **измерениями NOAA NCEI GHCNh**, а не с ERA5 или другими модельными реконструкциями:

- сопоставление станции **по точному коду ВМО**, с проверкой координат: никакой незаметной подмены соседним пунктом;
- в расчёт попадают только наблюдения температуры, помеченные флагом качества NOAA `1`;
- допуск сопоставления по времени — не более 45 минут; интерполяция отсутствует;
- горизонты 24/48/72 ч, общий набор допустимых наблюдений для ECMWF, ICON и GFS;
- MAE, Bias, RMSE, P95, число сопоставлений, количество независимых дней;
- публикация рейтинга только при **20+ наблюдениях минимум за 5 разных дней** для *каждой* модели.

Если наблюдений недостаточно, публикуется `insufficient_samples`, а победитель остаётся `null`. Результат описывает погоду **на метеостанции**, которая может находиться за пределами городской застройки. Отдельные источники GHCNh могут по-разному кодировать качество, поэтому текущий допуск консервативен; для отдельных станций необходима дополнительная проверка источника.

## Автоматизация и тесты

| Workflow | Назначение |
|---|---|
| [weather-collect.yml](../../.github/workflows/weather-collect.yml) | Каждые 6 ч сохраняет прогнозы |
| [weather-verify.yml](../../.github/workflows/weather-verify.yml) | Ежедневно пересчитывает точность по данным NOAA |
| [weather-historical.yml](../../.github/workflows/weather-historical.yml) | Еженедельно проверяет архивные прогнозы за последние 90 дней по Open-Meteo Previous Runs и NOAA |
| [weather-ci.yml](../../.github/workflows/weather-ci.yml) | Проверяет регрессионные Python-тесты, JavaScript и формат JSON |
| [weather-pages.yml](../../.github/workflows/weather-pages.yml) | Публикует сайт из Actions, каждые 6 часов подхватывает новые метрики |

Первичное включение Pages выполняется в настройках репозитория: **Settings → Pages → Source: GitHub Actions**. Обычный `GITHUB_TOKEN` не может создать отсутствующий Pages-сайт. Коммиты из Actions, подписанные `GITHUB_TOKEN`, не запускают последующие workflows по событию push, поэтому Pages имеет собственное расписание.

Локальные тесты:
```bash
python3 -m unittest discover -s weather/tests -p 'test_*.py' -v
python3 -m http.server 8080
# открыть http://localhost:8080/weather/
```

## Исторический бэктест

`scripts/historical.py` использует **Open-Meteo Previous Runs API** с фиксированными заблаговременностями 24/48/72 часа и результаты наблюдений **NOAA GHCNh** за последние 90 дней, исключая три последних дня на случай задержки публикации наблюдений. Это отдельная методология, а не операционная оценка снимков `captured_at`; обе таблицы показываются отдельно. Для публикации сравнения требуется от 100 общих почасовых наблюдений за не менее чем 20 различных дней. Отсутствующие станции или недоступные исторические модели приводят к прочеркам.

Исходные архивные модели: `ecmwf_ifs025`, `gfs_global`, `icon_global`; при недоступности любого из трёх прогнозов сравнение не объявляет победителя. **Наличие скрипта и расписания не означает, что реальная историческая выборка уже успешно получена или что Localzet Weather доказанно точнее конкурентов.** Проверить запуск можно в [Actions / Historical backtest](https://github.com/localzet/localzet.github.io/actions/workflows/weather-historical.yml).
